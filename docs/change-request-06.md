## 0. 结论速览

1. **未付**改为申请口径：`max(0, applied − paid)`，不再用 `due − paid`。
2. **未申请**新增：`max(0, due − applied)`，同样纯展示。
3. 三个异常数**互不替代**，不得静默吞掉：
   - 超付申请 = `max(0, paid − applied)`（付款超出申请）；
   - 超应付 = `max(0, paid − due)`（旧「超付」，列名改为「超应付金额」）；
   - 超额申请 = `max(0, applied − due)`。
4. 合同变更冻结对象统一为 `PaymentNode.has_business`：**已申请 / 已开票 / 已付款任一发生即冻结**，不再只看 `paid > 0`。
5. 冻结节点 `due/paid/applied/invoice/status/日期` 全部不动；变更差额只分给同科目未冻结节点，合同总额守恒。
6. 不做数据库迁移：全部由现有 `due_amount/applied_amount/invoice_amount/paid_amount` 派生，不写库。
7. 主表、报表、导出共用同一套公式；报表/导出保留「未付异常备注」列。

## 1. 口径定义

### 1.1 基础量（均来自 `payment_nodes`）

| 量 | 字段 | 说明 |
|---|---|---|
| 应付 | `due_amount` | 合同约定该节点应付 |
| 已申请 | `applied_amount` | 付款申请累计（一张申请可多笔付款） |
| 已开票 | `invoice_amount` | 发票累计 |
| 已付款 | `paid_amount` | 出纳实付累计，系统只记录 |

### 1.2 派生公式与显示

| 指标 | 公式 | 异常（纯展示） | 显示位置 |
|---|---|---|---|
| 未付 | `max(0, applied − paid)` | `paid > applied` 时该值显示 0，同格红标 **「超付申请 ¥X」**，`X = paid − applied` | 详情主表、报表、导出 |
| 未申请 | `max(0, due − applied)` | `applied > due` 时该值显示 0，同格红标 **「超额申请 ¥X」**，`X = applied − due` | 详情主表、报表、导出 |
| 超应付金额 | `Σ max(0, paid − due)` | 旧「超付金额」列改名，语义不变 | 报表、导出 |
| 超付申请 | `max(0, paid − applied)` | 只用于「超付申请」标记，不单独加金额列 | 报表异常备注、导出备注、详情红标 |
| 超额申请 | `max(0, applied − due)` | 只用于「超额申请」标记 | 报表异常备注、导出备注、详情红标 |

规则：

- 任何派生值**不出现负数**，不为负去写库，不修改 `status`、`change_note` 或任何金额列。
- `paid > applied` 与 `applied > due` 可同时存在；两处红标分别显示，不互相覆盖。
- 「超付申请」≠「超应付」≠「超额申请」：一个看申请，一个看应付，一个看申请超应付，禁止合并成一个「超付」。
- 导出新增一列「未付异常备注」：按「超付申请 ¥X；超额申请 ¥Y」拼接，无异常留空；两个都有时都要写。
- 异常不阻断业务（只提示）；历史/导入数据只做展示兜底。
- 金额格式统一 `fmt_money`（两位小数、¥ 前缀）。

### 1.3 口径示例（单节点，应付 300,000）

| 场景 | 已申请 | 已付 | 未付 | 未申请 | 异常标记 |
|---|---:|---:|---:|---:|---|
| 正常已付清 | 300,000 | 300,000 | 0 | 0 | — |
| 申请未付清 | 300,000 | 100,000 | 200,000 | 0 | — |
| 有付款无申请 | 0 | 100,000 | 0 | 300,000 | 超付申请 ¥100,000 |
| 申请超应付（历史） | 320,000 | 0 | 320,000 | 0 | 超额申请 ¥20,000 |
| 付款超申请且超应付 | 300,000 | 320,000 | 0 | 0 | 超付申请 ¥20,000；超应付 ¥20,000 |

> 第 4 行「未付 320,000」是 `applied − paid` 的原值，说明申请本身已超应付；不要再用 due 截断，否则会掩盖「超额申请」。

## 2. 合同变更冻结与重算

### 2.1 冻结判定（唯一口径）

```python
def node_is_frozen(node):
    return node.has_business   # 已申请/已开票/已付款/状态非未触发/存在申请单或发票
```

`has_business` 定义在 `app/models.py:159-170`，已覆盖：

- `status != '未触发'`；
- `applied_amount > 0`；
- `invoice_amount > 0`；
- `paid_amount > 0`；
- 存在 `applications` 或 `invoices` 记录。

**删除**现有的 `paid_amount > 0` 局部判定：`app/routes.py:2291`、`app/validation.py:491-492`、`app/templates/contract_change.html` 中的 `paid_amount > 0` 过滤，全部改为 `has_business`（模板用已冻结节点列表渲染）。只申请、未开票未付款的节点从此也冻结。

### 2.2 重算算法（逐科目）

1. 读取该科目 `new_total`（变更后总额）。
2. `frozen = [n for n in item.nodes if n.has_business]`；`frozen_due = Σ frozen.due_amount`。
3. 若 `new_total < frozen_due`：阻断，提示「小于冻结节点应付合计」。
4. `unfrozen = [n for n in item.nodes if not n.has_business]`；`remaining = new_total − frozen_due`。
5. 若 `unfrozen` 为空：
   - `remaining == 0`：该科目无需调整，通过；
   - `remaining != 0`：阻断，提示「全部节点已冻结」。
6. 否则按未冻结节点**原应付金额**占比分摊 `remaining`；若未冻结应付合计为 0，退回按 `ratio` 占比；再为 0 则按节点数均分。
7. 用 `money.allocate_tail` 归集尾差，顺序 `warranty → acceptance → progress → first`；只写未冻结节点的 `due_amount`。
8. 冻结节点：`due_amount/paid_amount/applied_amount/invoice_amount/status/due_date/trigger_date` 一律不改；可写 `change_note` 记录「变更前/后应付差异」，但不得改上述字段。
9. `item.additional_amount = new_total − item.original_amount`；`original_amount` 不变。
10. 校验 `Σ item.new_total == 变更后合同总额` 且 `Σ node.due_amount == Σ item.new_total`。

### 2.3 数字例子：100 万 → 110 万

变更前：合同 1,000,000；首付 300,000（已申请且已付）；进度 520,000、验收 150,000、质保 30,000（均未动）。

变更后合同总额 1,100,000：

- 冻结：首付，`frozen_due = 300,000`；
- 差额：`1,100,000 − 300,000 = 800,000`；
- 未冻结原应付权重：520,000 : 150,000 : 30,000（合计 700,000）；
- 分摊：进度 594,285.71、验收 171,428.57、质保 34,285.71；尾差 0.01 归质保 → **34,285.72**；
- 节点合计：300,000 + 594,285.71 + 171,428.57 + 34,285.72 = 1,100,000.00。

变更后展示：

| 节点 | 应付 | 已申请 | 已付 | 未付 | 未申请 |
|---|---:|---:|---:|---:|---:|
| 首付（冻结） | 300,000.00 | 300,000.00 | 300,000.00 | 0 | 0 |
| 进度 | 594,285.71 | 0 | 0 | 0 | 594,285.71 |
| 验收 | 171,428.57 | 0 | 0 | 0 | 171,428.57 |
| 质保 | 34,285.72 | 0 | 0 | 0 | 34,285.72 |
| 合计 | 1,100,000.00 | 300,000.00 | 300,000.00 | 0 | 800,000.00 |

若首付只是**已申请未付款**（300,000/0）：仍冻结，应付保持 300,000；未付 = 300,000（这是申请余额，不是变更新增的未付），未申请 = 0。冻结的含义是「金额不随合同变更重算」，不是「把未付变成 0」。

### 2.4 阻断与提示文案

| 条件 | 处理 | 建议文案 |
|---|---|---|
| `new_total < frozen_due` | 阻断 | 科目「X」变更后总额 ¥A 小于冻结节点应付合计 ¥B，无法变更 |
| 全部节点已冻结且 `remaining != 0` | 阻断 | 科目「X」全部节点已冻结（申请/开票/付款任一发生），变更后总额必须等于冻结节点应付合计 ¥B |
| `Σ new_total <= 0` / 所有科目未变化 | 阻断 | 沿用现有文案 |
| 存在 `超付待处理` 节点 | 阻断 | 沿用现有文案（历史超付先处理） |
| 其余异常（超付申请/超额申请） | **不阻断** | 仅展示红标 |

### 2.5 禁止事项

- 不得把冻结节点 `due_amount` 改成 `paid_amount` 来让「未付 = 0」：会造成账实不符，且丢失合同应付依据。
- 不得因合同变更修改冻结节点的 `paid/applied/invoice/status`。
- 不得在冻结节点上重新按新总额 × 比例计算 `due`。
- 不得只改前端隐藏差额；后端必须守恒并落审计。

## 5. 测试清单

### 5.1 派生公式（`tests/qa_db_cases.py`）

- `applied=paid=due` → 未付 0、未申请 0、无异常；
- `applied=due, paid=0` → 未付=due、未申请 0；
- `applied=0, paid>0` → 未付 0、未申请=due、备注「超付申请 ¥paid」；
