**最严重两条（带行号）**

1. **合同「修改/二次确认」会清空已发生的付款数据**（`app/routes.py:599-603`、`app/routes.py:610-617`）：更新路径先 `bulk delete` 全部付款节点再重建，绕过 ORM 级联。项目已有申请/付款记录时 `PRAGMA foreign_keys=ON` 直接抛 FK 异常返回 500；没有子记录时则**静默把发票金额、付款金额、节点状态、质保应付日期全部清零**。注释「已有付款记录不受影响」与实现相反。
2. **服务端完全不校验付款比例/金额口径**（`app/routes.py:583-587`，`ratio_sum` 算完从未使用）：直接 POST 即可提交比例合计 105%（生成应付 168,300 > 合同 165,000）或负比例（首付款 -16,500），且无审计。`scripts/e2e_test.py:253-257` 的「重复确认」用例实际把项目金额改成了 1 元，只因随后 10.10 又改回来才没暴露。

**Chief 追加两点的结论**

- **审计与留痕：缺失，判定为上线阻断（P0-4）。** 系统只有分散的 `created_at / applicant / operator` 字段，没有 `updated_at`、没有「谁在何时把哪个金额/状态从什么改成什么」的操作日志，项目/科目/节点金额与状态、验收/试运行日期、合同确认回改均可被直接覆盖且无痕迹，项目/用户为物理删除不可恢复。替换 Excel 后一旦出现付款争议或误操作，无法举证。
- **Excel 迁移：目前没有导入能力，且模型缺字段、状态口径也承载不了旧台账（P0-6）；没有导出/下载能力（P0-5）。** 只有 `scripts/init_db.py` 硬编码的单项目种子数据。缺：导入入口与批次/幂等/回滚、合同编号与供应商/签订日期等主数据字段、发票日期与计划付款日期、多张发票、**部分付款状态**、已开票未申请状态、多次试运行历史；报表页只能网页查看，无任何 Excel/CSV 下载（全仓无 `send_file`/`openpyxl`/`csv` 导出代码）。

**一句话定性**：单机演示可用，但作为「单位内部真上线、替换 Excel」的财务台账，缺口集中在**审计留痕、合同回改的数据破坏、服务端金额校验、导入导出、并发控制**五处；按当前形态上线风险高。

**严重度口径**：P0 = 上线阻断 / 资金或数据事故；P1 = 特定场景错误或合规硬伤；P2 = 隐患与改进项。

## 一、P0 问题（6 条）

### P0-1 合同「修改 / 二次确认」清空已发生付款数据（数据不可恢复 / 500）

- **位置**：`app/routes.py:557-654`（入口 `557-566`，更新分支 `589-621`，删节点 `599-603`，重建 `610-617`）；模型关系 `app/models.py:101-118`（`PaymentNode.applications` cascade）、`app/models.py:105,106`（FK `project_id`/`item_id`）。
- **现象**：
  1. 已确认合同再次打开确认页并提交（即「修改」功能，README:77 描述为正常功能），走 `is_update` 分支，先 `PaymentNode.query.filter_by(project_id=...).delete()`，再删 `ProjectItem`，然后重建「合同价款」科目 + 4 个节点，状态一律 `未触发`、金额按表单重算。
  2. 若项目下已有 `payment_applications` / `payment_records`（FK 指向 `payment_nodes`），`Query.delete()` 不触发 ORM cascade，且连接已 `PRAGMA foreign_keys=ON`（`app/__init__.py:70`）→ 删除语句直接 FK 失败，请求 500。
  3. 若没有子记录（如 Excel 迁移/手工回填的汇总数据，`scripts/init_db.py:53-62` 就是这种形态），删除成功 → **发票金额、付款金额、节点状态、质保金应付日期、进度款触发日期全部丢失**，且无任何提示。
  4. 重建后没有调用 `sync_project_dates`：项目的 `acceptance_date`/`warranty_due_date` 还在，但节点的 `due_date`/`trigger_date` 全为 NULL，页面与报表口径分叉。
- **为什么错**：付款节点是付款进度的事实载体，回改合同金额/比例不能用「删了重建」实现；删除未走级联/未做数据保护；更新路径只保护了项目编号，没有保护交易数据。
- **复现/验证**：
  - 探针 T3（项目有 1 条申请 + 1 条付款记录）→ 提交确认 → `500`，数据未被破坏（事务回滚）。
  - 探针 T5（项目有 `invoice_amount=60000 / paid_amount=60000 / status=已付款`，无子记录）→ 提交确认 → `302`，随后节点变为 `invoice=0 / paid=0 / status=未触发`，科目增补金额 50000 被清零，项目组日期仍在而节点日期为 NULL。
  - 手工复现：任一已确认合同 → 合同列表「修改」→ 直接提交（不改任何值）即可。
- **影响**：付款台账被静默清空/改写；若回改发生在财务已付款后，属资金数据事故，且无法追溯。
- **建议改法（本次不改）**：
  1. 区分「口径变更」与「交易数据」：金额/比例变更只更新 `PaymentNode.due_amount`/`ratio`/`node_name`，绝不删除节点；合同金额变动改为「差额调整」，生成调整记录而不是重建。
  2. 若必须重建，先做前置校验：项目下存在申请/付款记录、或节点已触发/已开票/已付款时禁止重建，提示走「变更单」；并保留原节点为历史版本（`is_active` 标记/历史表）。
  3. 更新路径补 `sync_project_dates`，并重算 `warranty_due_date`。
  4. 删除改为 ORM 级联或显式事务 + 失败回滚提示；`PaymentNode` 与 `PaymentApplication/PaymentRecord` 建立 `ON DELETE RESTRICT` 并给出业务错误页而不是 500。

### P0-2 已确认合同的确认页回填「旧识别值」而非项目现值，一提交就覆盖

- **位置**：`app/templates/contract_confirm.html:48-60`（原金额取 `result.contract_amount`，**增补金额硬编码 `value="0.00"`**）、`:103-113`（比例取 `result.nodes` 的识别值）、`app/routes.py:565-587`（提交值全部来自表单，未与项目现值比对）、`app/routes.py:610-617`（重建节点）。`result_json` 从未在确认后回写（`app/routes.py:589-621` 只更新 `contract_name`）。
- **现象**：对已确认合同点「修改」，表单显示的是当初的识别结果——增补金额永远 0.00、比例是识别比例；项目当前真实值不可见。用户「只改一个比例」提交时，会把未被显示的增补金额清零、把上次人工改过的比例改回识别值。
- **为什么错**：修改表单的数据源应为项目现值（`ProjectItem` / `PaymentNode`），而不是历史识别快照；`result_json` 也不保存 `additional_amount`，因此页面无从显示。
- **复现/验证**：探针 T4——项目实际增补 50,000、节点比例 25%，确认页仍渲染 `additional_amount=0.00`、`ratio_first=30.00%`；随后 T5 提交即把增补清零（与 P0-1 叠加成完整的数据丢失链路）。
- **影响**：用户以为在「微调」，实际改掉整份金额口径；无审计、无二次确认。
- **建议改法**：确认页按 `contract.project_id` 读取项目现值回填（原金额=科目原金额、增补=科目增补、比例=节点比例）；`result_json` 增补写入 `additional_amount`；提交时服务端对「现值 vs 提交值」做差异清单并要求用户显式确认，差异写入审计日志（P0-4）。

### P0-3 服务端零校验：比例合计、正负、金额范围、NaN/Inf 全部放行

- **位置**：`app/routes.py:583-587`（`ratio_sum` 逐项累加后**从未使用**，无任何判断）；`app/routes.py:577-579`（只校验原金额 > 0）；`app/routes.py:610-617`（按比例直接算应付）；`app/routes.py:792-796`（`_to_num` 用 `float` 且无有限数校验）；前端校验仅 `app/templates/contract_confirm.html:159-181` 的 `recompute()`，可绕过。
- **现象**：
  - 直接 POST `ratio_warranty=5`（合计 105%）→ 接受，应付合计 168,300 > 合同 165,000；
  - `ratio_first=-10` → 接受，首付款应付 **-16,500**，节点名「首付款-10%」；
  - 金额输入 `nan`/`inf`/`1e309` 通过 `_to_num`（`float('nan')`/`float('inf')`），可能写入 NULL/Inf 或在 MSSQL 转换时报错；
  - 比例合计 90%/合计金额 ≠ 合同金额都没有校验（关闭 JS 或直接 POST 即可）。
- **为什么错**：财务台账的应付合计必须与合同金额勾稽，且比例/金额必须为正、有限、在合理区间；校验放在前端等于没有校验。
- **复现/验证**：探针 T2a/T2b/T13（均 302 成功，节点金额已实测为 168,300 / -16,500 / NaN、Inf）。
- **影响**：可生成超过合同额或负数的应付台账，报表/付款申请直接引用错误金额；一旦结合 P0-1 的「修改」功能，等于允许任意改写应付。
- **建议改法**：服务端统一校验并拒绝（400/表单回显）：各比例 ∈ [0,100]，合计 = 100%（容差 0.01，或允许合计≠100 但必须二次确认并记录）；原金额/增补金额为 Decimal 有限数且 ≥ 0（增补为负需业务确认）；节点应付合计与「合同金额」差 ≤ 0.01（尾差归入最后一个节点）；`_to_num` 改用 `Decimal` + `is_finite()`，拒绝 `nan/inf/科学计数`；金额上限按 `Numeric(14,2)` 定义校验。

## 二、P1 问题（9 条）

### P1-1 增补金额口径导致「节点应付合计 ≠ 合同总额」（差额 = 30% × 增补）

- **位置**：`app/routes.py:180-187`（按 `NODE_TEMPLATES` 生成节点）、`app/__init__.py:9-38`（首付款 `calc_base='original'`，其余 `'total'`）、`app/models.py:87-89,120-127`（`total_amount = 原 + 增补`）、`app/routes.py:610-617`（合同路径同样：首付按原金额，其余按原+增补）。
- **现象**：原金额 100,000、增补 50,000 时，4 个节点应付合计 = 100,000 + 0.7×50,000 = **135,000**，而项目「合同总额」显示 **150,000**，差 15,000 = 30%×增补。合同生成的项目同样如此。`app/templates/project_detail.html:34-36` 同时展示「合同总额 150,000」与节点合计 135,000，页面自相矛盾。
- **为什么错/待确认**：README:14 明确「首付款按科目原金额，其余按原+增补」，若这是业务口径，则增补部分的 30% 永远不产生应付；若业务上增补应全额参与付款，则规则错。无论哪种，当前实现都没有提示，且报表「应付合计」与合同总额不一致，无法直接对账。
- **复现/验证**：探针 T1（`nodes=135000, contract=150000, gap=15000`）。
- **建议改法**：业务确认口径后二选一：(a) 增补也参与首付款（`calc_base='total'`），节点合计 = 合同总额；(b) 保持现状，则报表/详情页显式标注「增补金额 30% 不产生付款」，并把「合同总额」与「应付合计」分开统计。同时在 `recalc` 后做合计勾稽校验。

### P1-2 付款状态机缺失：可跳步、可回退、部分付款即「已付款」且无法补付

- **位置**：`app/routes.py:294-374`（`node_update` 三个 action 均不校验当前状态/金额上限）；申请 `302-327`（不校验是否已付款，直接覆盖 `node.status`）；付款 `344-373`（不校验是否已申请/已开票，`node.status='已付款'` 无条件赋值，`round(float(paid)+amount,2)` 无应付上限校验）；模板 `app/templates/project_detail.html:162-188`（UI 只对 `已申请` 显示付款表单）、`:180`（默认填 `due-paid`，但可改）。
- **实测行为**：
  - T8：已付款节点（已付 30,000）再次 POST `action=apply` → 状态回退为「未开票已申请」，已付金额仍在；
  - T10：`未触发` 节点直接 POST `action=pay` → 成功，状态「已付款」；
  - T9a：应付 30,000 只付 1,000 → 状态「已付款」；T9b：页面随即隐藏付款入口 ⇒ **尾款无法再登记**（只能直接构造 POST）。
- **为什么错**：付款节点需要严格状态机（未触发→已申请→已开票→部分付款→已付款）与金额约束（累计已付 ≤ 应付），状态与金额必须一致。
- **影响**：部分付款场景（真实业务常见）数据错误；状态回退导致报表「待付款/已付款」判断错误；可对未申请节点付款造成流程失控。
- **建议改法**：集中状态机与转移表（已在 `app/__init__.py:41` 定义了 `FLOW_STATUS` 却未使用）；每次转移服务端校验前置状态、金额范围（`paid_amount + amount <= due_amount + 容差`）、必填字段；新增「部分付款」状态或按 `paid_amount` 派生展示；页面允许补付并展示累计已付/未付；所有转移写审计。

### P1-3 日期联动单向：清空/改早不回退，验收可反复覆盖且影响已付款节点

- **位置**：`app/routes.py:69-83`（`sync_project_dates` 只在日期「有值」时联动，且内部 `db.session.commit()`）；`app/routes.py:218-237`（编辑页可把试运行/验收日期清空）；`app/routes.py:377-400`（验收可重复登记、无唯一约束、日期直接覆盖 `project.acceptance_date`）；`app/routes.py:403-418`（试运行日期不允许清空，与编辑页行为不一致）。
- **实测行为**：
  - T11：编辑清空试运行日期 → `project.trial_date=None`，但进度款节点 `trigger_date` 仍残留 2025-11-04；
  - T12：验收 2026-03-10 → 质保 2029-03-09；把质保金节点付款后再登记更早的验收 2025-01-01 → 项目验收日期被覆盖、质保金 `due_date` 回退为 2028-01-01，节点仍是「已付款」；无任何校验/审计。
- **为什么错**：验收/试运行日期直接决定「应付日期」与「提醒」，历史与已触发/已付款节点不能被事后改写；同一项目多次验收应保留记录且以最后一次/指定版本为准。
- **建议改法**：日期变更纳入审计（P0-4）；已触发/已开票/已付款的节点禁止因日期变更被改写（或只更新未触发节点，已发生节点保留原值并提示）；清空日期时同步清空对应触发/应付日期并二次确认；验收登记改为「不可覆盖」的版本化记录（项目上的 `acceptance_date` 取最新记录，旧记录保留）；试运行同样留历史；校验验收 ≥ 试运行、日期 ≤ 今天等（按业务）。

### P1-4 operator 越权修改项目状态（绕过管理员限制）

- **位置**：`app/routes.py:218-237`（`project_edit` 仅 `role_required('admin','operator')`，但 `app/routes.py:228` 无条件 `project.status = request.form.get('status')`，无白名单、无角色区分）；对照组 `app/routes.py:421-433`（独立的状态修改路由限 `admin`）；模板 `app/templates/project_detail.html:14-23` 只对管理员显示状态下拉，但 `app/templates/project_form.html:25-34` 编辑页对 operator 同样渲染状态下拉。
- **实测**：探针 T7——operator 直接 POST `/projects/<id>/edit` 带 `status=已归档` → 302 且项目变为已归档。另可写入任意非白名单字符串（如 `status=乱写`），因为无枚举校验。
- **为什么错**：权限控制写在模板/独立路由上，未在共享编辑路由上收口，属典型「UI 隐藏 ≠ 权限」。
- **建议改法**：`project_edit` 拆字段权限：operator 只能改名称/备注/日期（且日期按 P1-3 规则），状态只允许 admin（走统一状态机路由）；服务端白名单校验 `status in {'进行中','已完成','已归档'}` 及合法转移（如已归档不可回「进行中」，需管理员解除）。

### P1-5 删除用户触发 FK 500（有项目/申请/付款/合同引用时）

- **位置**：`app/routes.py:774-787`（`user_delete` 只拦自己，无引用检查）；模型无 `ON DELETE` 策略：`app/models.py:44`（`Project.created_by`）、`:155`（`PaymentApplication.applicant_id`）、`:182`（`PaymentRecord.operator_id`）、`:212`（`ContractFile.created_by`）。
- **实测**：探针 T6——删除有 `created_by` 引用的用户 → **500**（`FOREIGN KEY constraint failed`），用户未被删除，页面无友好提示。
- **为什么错**：用户是弱引用（业务上应保留历史操作人），删除前需处理引用（禁删/SET NULL/软删除）。
- **建议改法**：用户改软删除（`is_active=false`），历史引用保留；或 FK 改 `ON DELETE SET NULL` + 前置检查；删除前统计引用并提示「该用户有 N 个项目/N 条付款记录，只能停用」；所有用户管理操作写审计。

### P1-6 金额全链路 float + Python `round`（银行家舍入），存在 1 分误差与合计不勾稽

- **位置**：`app/routes.py:58-62`（`fmt_money` 转 float）、`:792-796`（`_to_num` round float）、`:127,290,713-719`（float 累加）；`app/models.py:120-127`（`round(float(base)*float(ratio), 2)`）、`:95-97`（`to_dict` 转 float）；合同路径 `app/routes.py:610-617`（直接 `round(base*ratio,2)`）；模板统一用 float 格式化（`app/templates/project_detail.html:108-110,151-153`）。
- **实测**：探针 T14——科目 100.30、验收款 15%：系统算出 **15.04**，财务四舍五入（ROUND_HALF_UP）应为 **15.05**（`round(15.045,2)` 因二进制表示与银行家舍入落到 15.04）。
- **为什么错**：金额必须用 Decimal 定点运算与统一舍入规则；float 还会在大额累加、报表合计、导出对账时产生分差；SQLite 不强制 `Numeric(14,2)` 精度，掩盖问题，MSSQL 下会暴露。
- **建议改法**：定义统一金额工具（`Decimal` + `ROUND_HALF_UP` + `quantize(0.01)`），模型存取统一 Decimal；`_to_num` 改 Decimal 解析并校验；每个节点计算后与合同/科目金额做尾差校验与明确归集；报表合计用 Decimal；导出按同一口径。

### P1-7 并发/幂等缺失（双击、多用户、多请求）

- **位置**：`app/routes.py:65-66`（`apply_no` = 秒级时间+微秒%1000，碰撞即 500，`app/models.py:149` 唯一约束）；`app/routes.py:453-460`（项目编号 `SELECT max + 1`，无锁无重试，并发重复编号 → 500）；`app/routes.py:557-654`（合同确认先读 `status` 再写，无幂等键/锁 → 双击/并发可重复建项目或重复改写）；`app/routes.py:344-373`（`paid_amount` 读改写无锁 → 并发付款丢失更新）；`app/routes.py:334-341`（发票/申请回填同样读改写）。
- **为什么错**：单机 SQLite + 开发服务器掩盖了并发问题；「单位内部多用户」下双击提交、两人同时付款/开票是现实场景。
- **建议改法**：编号改数据库序列/号段表 + 唯一冲突重试；合同确认用幂等键（`contract_id + 版本`）与行级锁/乐观锁（`version` 列）；节点金额更新用原子 SQL（`UPDATE ... SET paid_amount = paid_amount + :amt WHERE ... AND paid_amount + :amt <= due_amount`）；关键写接口加提交按钮防重 + 事务内二次校验状态。

### P1-8 安全基线不足（CSRF / 默认密钥 / 默认口令 / 会话）

- **位置**：`app/__init__.py:48`（`SECRET_KEY` 默认硬编码，未配置即可用公开值伪造会话）；全仓**无 CSRF 防护**（所有 POST 表单无 token，grep 无 `csrf`）；`README.md:46-52` 与 `scripts/init_db.py:78-89`（默认口令 admin/admin123、jbr/123456、viewer/123456）；`app/routes.py:88-108`（无失败次数限制、无会话过期、`logout` 为 GET）。
- **为什么错**：金额与状态操作一旦被 CSRF 或会话伪造，可越权改账；默认口令 + 公开 SECRET_KEY 组合下，内网也存在横向风险。
- **建议改法**：引入 CSRF（Flask-WTF 或自建 token，覆盖所有 POST）；`SECRET_KEY` 强制环境变量、启动时校验非默认；首次登录强制改密、删除/禁用演示账号；session 加固（`PERMANENT_SESSION_LIFETIME`、`SESSION_COOKIE_SECURE/HTTPONLY/SAMESITE`）；登录失败限流/锁定；`logout` 改 POST；上线前置 HTTPS 反向代理。

### P1-9 报表/提醒口径问题

- **位置**：`app/routes.py:707-737`（`Project.query.all()` 全量、无状态过滤）；`:713-719`（`due/invoice/paid` float 累加，`unpaid = round(due-paid,2)` 可为负、`progress = paid/due*100` 可 >100）；`:721-723`（合计含已归档/已完成项目）；`:725-734`（提醒不区分项目状态，已归档项目仍提醒质保到期/待付款）；`app/templates/reports.html:53`（进度条宽度直接 `{{ r.progress }}%`，超 100% 溢出）。
- **为什么错**：台账口径未定义（是否含归档、超付如何展示），提醒对已完成项目无意义；报表是替代 Excel 的主要输出，口径必须固定并有说明。
- **建议改法**：明确并可配置口径（默认排除已归档，可勾选包含）；超付单独列「超付金额」并告警；进度按 `min(100, ...)` 展示但保留真实值；提醒只针对进行中项目；报表与导出（P0-5）同源计算；汇总金额用 Decimal。
