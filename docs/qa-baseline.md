## 一、结论摘要

**一句话：核心业务闭环能跑通（93 项 E2E 全过），但按「真上线」标准不具备条件。**

- **P0（上线阻断）3 项**：① 并发付款丢失更新（账实不符，3/3 复现）；② 无审计日志（谁在何时改金额/状态/删除不可追溯）；③ 无备份与恢复机制（数据库文件删除/损坏即全损，热备不可靠）。
- **P1（上线前应修）11 项**：经办人越权（删项目、经编辑改状态）、付款状态机缺失（可直付/超付/状态回退/归档后改账）、合同确认不校验比例与金额、已付款合同回改直接 500、增补金额 30% 无付款节点、金额舍入误差、默认 SECRET_KEY 可伪造管理员会话、全站无 CSRF、默认弱口令且无锁定、用 Flask 开发服务器无 HTTPS。
- **P2（可上线后迭代）11 项**：上传上限 16MB 与 README 20MB 不一致、默认英文错误页、日期清空后联动字段残留、非法状态可写入、种子数据口径矛盾、重新识别依赖启动目录、上传失败留孤立文件、并发同编号 500、图片 OCR 本机不可用且提示误导、无文件日志、依赖未锁版本且缺 Pillow。

**E2E 脚本结论不代表验收通过**：`e2e_test.py` 首跑 93/93，但第二次运行 88/5 失败（非幂等）；`e2e_scan_pdf.py` 在上传后未进入确认页即失败，且脚本仍以退出码 0 结束、无 PASS/FAIL 汇总——README 的「全部通过」不能作为上线依据。

## 五、数据准确性

### 5.1 种子项目对账（README 165,000 表）——全部通过

首付款 49,500.00 / 进度款 85,800.00 / 验收款 24,750.00 / 质保金 4,950.00 / 节点合计 165,000.00；试运行日期 2025-11-04；页面千分位展示正常。
质保口径验证：2026-03-10 → 2029-03-09（1095 天，跨 2028 闰年）；2024-02-29 → 2027-02-28，均通过。

### 5.2 增补金额口径——存在业务缺口（P1-06）

- 「首付款按原金额、其余按原金额+增补」逐项实现正确（原 100,000 + 增补 20,000：首付 30,000、进度款 62,400、验收款 18,000、质保金 3,600）。
- **但增补金额的 30% 没有对应付款节点**：节点合计 = 原金额 + 70%×增补 = 114,000，合同总额 120,000，**少 6,000 元**。增补越大缺口越大。
- 需业务确认这是否为口径本意；若否，则报表「应付合计」永远小于合同总额，存在漏付。

### 5.3 金额舍入——分位误差（P1-07）

系统用 `float` 相乘后 `round()`（Python 银行家舍入），非会计「四舍五入」：
`原金额 100.05 × 30%` 期望 30.02，实际 **30.01**（`100.05×0.3=30.014999…`）；`0.05×30%` 期望 0.02，实际 0.01。金额列虽为 `Numeric(14,2)`，但计算过程用 float，存在系统性分位偏差。

### 5.4 合同确认校验——缺失（P1-04）

- 比例合计 98%（30/50/15/3）被接受，节点合计 161,700 ≠ 合同额 165,000，服务端无拦截。
- 负比例 `-10` 被接受，生成 **-16,500 的负数应付节点**。
- 项目新建时负数原金额同样被接受，生成负数应付节点。
- 金额为 0/比例的边界、金额上限均无服务端校验（前端只有 JS 红色提示，可绕过）。

### 5.5 合同回改（修改金额/比例）

- 无付款记录时：回改比例/金额 → 更新原项目、不新建项目（E2E 10.10 通过）。
- **有付款记录时：回改金额（165,000→100,000）直接 500**，日志为 `sqlite3.IntegrityError: FOREIGN KEY constraint failed`（`routes.py:600` 删除节点未先清理申请/付款记录）；事务回滚后数据未丢，但功能不可用（P1-05）。
- 「重复确认拦截」在无付款场景实际是「更新原项目」，不新增项目（通过）。

### 5.6 状态流转——无状态机约束（P1-03）

- 节点「未触发」可直接登记付款（跳过申请/开票），实测成功且状态变「已付款」。
- 同一节点可重复付款并累计，已付 10,400 > 应付 5,200（超付）；付款记录 2 条。
- 已付款节点可再次「发起申请」，状态回退为「未开票已申请」。
- 项目「已归档」后仍可登记付款申请；「已归档→进行中」随意回退。
- 页面在已付款后隐藏操作按钮，但服务端不做校验，直接 POST 可绕过。

### 5.7 联动日期残留（P2-02）

登记试运行/验收后，通过「编辑项目」把日期清空：项目字段已清空，但进度款节点 `trigger_date`、质保到期日、质保金节点 `due_date` **残留旧值**，报表仍显示质保提醒。

### 5.8 种子数据口径矛盾（P2-04）

种子项目 3 个进度款节点 `paid_amount` 已为 68,120/14,560/3,120（合计 85,800），但状态为「已申请」。README 写「进度款已开票并处于已申请状态」。报表按 `paid_amount` 统计「已支付」，导致节点状态与报表口径不一致。

| 场景 | 实测结果 | 判定 |

| SQLite WAL / busy_timeout | `journal_mode=wal`，busy_timeout=5000；本次测试无锁超时 | ✅ 通过 |
| 服务运行中删除 DB 文件 | Windows 文件锁拒绝（WinError 32），运行中删不掉 | ✅ 有保护 |

| `init_db.py --force` | 无二次确认直接删库重建；本次验证 3 次 --force 均清空历史数据，不可恢复 | **P0-03** |

| 生产部署形态 | `app.run()` Flask 开发服务器（启动即警告 "Do not use it in a production deployment"），无 HTTPS、无反向代理配置 | P1-11 |

**备份结论（只给结论）**：当前系统**没有可用的备份/恢复能力**。若要保证数据不丢，上线前必须由外部手段提供「停服窗口整库复制」或「SQLite 在线 backup API + 定期校验 + 异地保留」；直接复制单个 `.db` 文件一定会丢最近已提交的数据，复制三件套也不可靠。

## 七、审计能力（P0-02）

结论：**无法回答「谁在什么时候改了金额或状态」**。

证据：
- 库表仅 `users / projects / project_items / payment_nodes / payment_applications / payment_records / acceptance_records / contract_files`，**无审计日志/历史表**。
- `payment_nodes`、`projects` 均无 `updated_at`、`updated_by` 字段；`contract_files` 只有 `created_by/created_at`，无 `confirmed_by/confirmed_at`；验收记录无登记人。
- 项目删除为物理删除（节点/申请/付款记录一并 DELETE），无软删标记、无回收站、无删除日志。
- 部分可追溯：付款申请单/付款记录存有申请人/操作人姓名；项目与合同存有创建人。但金额与状态的**修改**（合同回改、节点状态变更、项目状态变更、试运行/验收回填）均不记录操作者与时间。

对付款类系统，这是合规与追责的硬缺口，按上线阻断处理。

## 八、缺陷清单

### P0（上线阻断，共 3 项）

#### P0-01 并发付款丢失更新，账实不符
- **现象**：两个操作员同时给同一付款节点各登记 1,000 元，付款记录生成 2 条，但节点「已支付金额」只有 1,000 元（3/3 复现）。
- **复现步骤**：
  1. `init_db.py --force` 后启动服务；管理员新建项目「QA-LU」，原金额 10,000（首付款应付 3,000）。
  2. 取该项目首付款节点 id，用两个会话同时 POST `/nodes/<id>/update`，`action=pay&paid_amount=1000`（并发屏障同时发出）。
  3. 查询 `payment_nodes.paid_amount` 与 `payment_records` 条数：记录 2 条，`paid_amount=1000`。
- **影响**：付款台账与流水不一致，直接导致对账错误、重复付款/漏记，属于资金类数据错误。
- **建议**：付款金额改为数据库原子更新（`UPDATE ... SET paid_amount = paid_amount + :amt`）或 `SELECT ... FOR UPDATE`/乐观锁；付款请求加幂等键；并发用例纳入回归。

#### P0-02 无审计日志，金额/状态/删除不可追溯
- **现象**：系统没有任何审计表或操作日志；改金额、改状态、删除项目、合同确认回改均无「谁、何时、改前/改后」记录。
- **复现步骤**：
  1. 管理员新建项目并登记一笔付款，再由合同确认页修改合同金额/比例重新生成节点。
  2. 查询全部表：无审计/历史表，节点/项目表无 `updated_*` 字段，合同表无确认人/确认时间。
  3. 删除项目后查询：项目及关联数据物理消失，无删除痕迹。
- **影响**：无法追责、无法满足内部审计/财政检查，发生争议时无证据链。
- **建议**：增加操作日志表（操作人、时间、对象、动作、变更前后值、IP）；关键表加 `updated_at/updated_by`；删除改软删；合同确认记录确认人与时间。

#### P0-03 无备份与恢复机制，数据一旦删除/损坏即全损
- **现象**：系统没有任何备份/恢复入口或调度；`init_db.py --force` 无确认直接删库；数据库文件缺失或损坏后服务直接 500，只能重建空库。
- **复现步骤**：
  1. 停止服务，删除 `instance/payment_progress.db`（或写入垃圾字节损坏），启动服务。
  2. 打开登录页正常，提交登录 → 500（`no such table: users` / `file is not a database`），无提示、无自愈。
  3. 对运行中的库只复制 `.db` 单文件作为备份，再查询备份：丢失 WAL 中最近已提交数据。
- **影响**：误操作/勒索/磁盘故障即全部付款数据丢失，且无法恢复；不满足上线运行的基本要求。
- **建议**：上线前提供外部备份方案（停服整库复制或 SQLite backup API 定时任务 + 保留策略 + 定期恢复演练）；`--force` 增加二次确认与删前自动备份；补启动自检与友好提示。

### P1（上线前应修复，共 11 项）

#### P1-01 经办人可删除项目（越权、破坏性、无审计）
- **复现**：管理员建项目 → 以 `jbr/123456` 登录 POST `/projects/<id>/delete` → 302，项目及关联付款记录被删除；README 未授予经办人删除权限。
- **影响**：业务经办人可清空付款台账，且无痕迹（叠加 P0-02）。
- **建议**：删除仅管理员可用，或改为软删除+审批。

#### P1-02 经办人经「编辑项目」修改状态，绕过管理员专属路由
- **复现**：`jbr` POST `/projects/<id>/edit`，带 `status=已归档` → 302 且状态变为「已归档」；同样请求走 `/projects/<id>/status` 则被拒。
- **影响**：管理员专属权限形同虚设。
- **建议**：编辑路由不接受 status（或按角色白名单校验），统一走状态路由并做状态机校验。

#### P1-03 付款/项目状态机缺失
- **复现**：
  1. 新建项目，不发起申请，直接 POST `action=pay&paid_amount=100` → 节点直接「已付款」。
  2. 同一节点连续两次 `action=pay` 各 5,200（应付 5,200）→ 已付 10,400，状态仍「已付款」。
  3. 已付款节点再 POST `action=apply` → 状态回退「未开票已申请」。
  4. 项目状态改「已归档」后仍可对该项目节点发起付款申请。
- **影响**：付款流程可绕过、可超付、可篡改状态，账务不可信。
- **建议**：服务端状态机 + 金额上限校验（累计付款 ≤ 应付）、状态流转白名单、归档项目只读。

#### P1-04 合同确认不校验比例合计与金额合法性
- **复现**：上传样例合同 → 确认页比例填 30/50/15/3（合计 98%）提交 → 成功生成项目，节点合计 161,700 ≠ 165,000；比例填 `-10` → 生成 -16,500 应付节点；新建项目原金额填负数 → 生成负数节点。
- **影响**：错误合同参数直接进入付款计划，造成多发/少发。
- **建议**：服务端校验比例合计=100%、单比例 0–100、金额>0 且上限合理；与前端提示一致。

#### P1-05 已付款合同回改金额/比例 → 500
- **复现**：上传样例 → 确认生成项目（165,000）→ 首付款登记申请+发票+付款 49,500 → 再在确认页把金额改为 100,000 提交 → 500；日志 `FOREIGN KEY constraint failed`（`routes.py:600`）。
- **影响**：合同金额需要更正时功能不可用；若用于生产会阻塞业务。
- **建议**：更新分支先按节点删除申请/付款记录（或保留历史并禁止回改已付款节点），并给用户明确提示。

#### P1-06 增补金额的 30% 无付款节点（业务口径缺口）
- **复现**：新建项目原金额 100,000、增补 20,000 → 4 类节点合计 114,000，而项目合同总额 120,000，差 6,000（= 增补×30%）。
- **影响**：付款计划漏计，报表应付合计永远小于合同总额；增补越多缺口越大。
- **建议**：与业务确认口径；若增补也应付，需增加对应节点或调整后续比例基数。

#### P1-07 金额舍入不符会计口径
- **复现**：新建项目科目原金额 100.05 → 首付款应付 30.01（100.05×0.3=30.015，会计四舍五入应为 30.02）；0.05 → 0.01（应 0.02）。
- **影响**：分位金额偏差累积，财务对账差异。
- **建议**：全程用 `Decimal` + `ROUND_HALF_UP`，与 Excel 口径一致；对账用例覆盖边界值。

#### P1-08 会话/密钥安全（可伪造管理员会话）
- **复现**：
  1. 不设置 `SECRET_KEY` 启动服务，用源码默认密钥 `payment-progress-secret-key-change-in-prod` 签名 `{'user_id': 1}` 的 Cookie，访问 `/admin/users` → 200（管理员权限）。
  2. 登录响应 Cookie 无 `Secure`/`SameSite`/过期时间。
  3. 重启服务后旧 Cookie 仍可直接使用（200）。
- **影响**：任何能拿到源码的人可提权为管理员；Cookie 可被重放；无失效机制。
- **建议**：强制环境变量密钥（缺失拒绝启动）、`Secure/SameSite=Lax`、会话超时与登录后轮换、敏感操作二次确认。

#### P1-09 全站无 CSRF 防护
- **复现**：任意页面表单无 token；用脚本直接 POST `/projects/<id>/delete`、`/admin/users/<id>/delete`、`/nodes/<id>/update` 均无需 token 即成功。
- **影响**：结合浏览器默认 Lax 有一定缓解，但非系统级防护；内网钓鱼页可诱导操作。
- **建议**：引入 Flask-WTF/CSRF token 或 SameSite+Origin 校验；`/logout` 改 POST。

#### P1-10 默认弱口令且无登录保护
- **复现**：`admin/admin123`、`jbr/123456`、`viewer/123456` 直接登录；连续 6 次错误密码后立即正常登录（无锁定/延迟）。
- **影响**：公网/内网弱口令爆破风险；默认账号公开在 README。
- **建议**：首次登录强改密、密码复杂度、失败锁定/延迟、禁用/改默认账号。

#### P1-11 生产部署形态不达标
- **复现**：`run.py` 使用 `app.run()`；启动即打印 "WARNING: This is a development server. Do not use it in a production deployment."；无 HTTPS/反向代理配置。
- **影响**：多用户并发、稳定性、安全性均不满足生产要求。
- **建议**：Windows 上使用 waitress（或 IIS/nginx + WSGI），配置 HTTPS、访问日志与进程守护。

## 九、测试脚本与文档本身的问题（按首席要求单列）

`scripts/e2e_test.py`：

3. **断言写死绝对值**（如 viewer 后节点金额必须=30,000），复用性差。

`scripts/e2e_scan_pdf.py`：
1. **失败仍退出码 0**：上传未到确认页只 print 后 return，CI/人工都会误判为通过；无 PASS/FAIL 汇总。
2. **不输出服务端失败原因**：只提示「未重定向到确认页」，不显示 `contract_files.error_msg`，本次真实原因（WinRT 文件访问拒绝被包装成「未安装 OCR 语言包」）无法从脚本直接看出。

`README.md`：
1. 声称上传「单个文件不超过 20MB」，实际代码 `MAX_CONTENT_LENGTH=16MB`。
2. 声称 e2e「全部通过」即验证通过，但脚本不覆盖上述关键项，且扫描件脚本失败不报错。

`requirements.txt`：
