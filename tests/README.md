# tests 目录说明（QA 回归）

## 一、怎么跑

在项目根目录执行一条命令：

```bash
python tests/run_qa.py
```

- 需要依赖与运行环境一致（Flask / Flask-SQLAlchemy / pdfplumber / python-docx / PyMuPDF / requests / Pillow）。
- 可选参数：`--json result.json` 另存 JSON 结果；`--keep-temp` 保留临时目录便于排错。
- 退出码：`0` = 无 FAIL 且无 XPASS；`1` = 出现 FAIL 或 XPASS（缺陷状态变化需更新用例/基线）。

## 二、数据与环境（默认安全）

- 每次运行自动创建**临时目录数据库**，用 `scripts/init_db.py` 的种子逻辑写入 3 个默认用户 + `PJ-2025-DSJ` 种子项目；
- 用 `werkzeug` 在**随机端口**起真实 HTTP 服务（进程内），结束自动停止；
- 合同上传目录在测试内被重定向到临时目录；
- **绝不读写项目内的 `instance/payment_progress.db`**，也不启动/占用 5001 端口；
- 运行结束自动清理临时的库、上传文件与服务进程。

状态含义：

| 状态 | 含义 |
| --- | --- |
| PASS | 符合预期 |
| FAIL | 与预期不符，必须排查（退出码 1） |
| XFAIL | 已知缺陷的验收用例，当前按预期失败（不阻断退出码） |
| XPASS | 缺陷疑似已修复但用例未更新，需核对后摘掉 `xfail` 标记并更新本文件 |

## 五、当前 XFAIL（已知缺陷，按基线报告编号）

**1 项：CR04-01 — 申请单号生成器重复 → 并发申请偶发 500**

- 断言：`app/routes.py:167-169 make_apply_no()` 连续生成 5000 个单号必须唯一（确定性用例）。
- 实测：5000 次仅约 16~17 个唯一值。单号 = `AP` + 秒级时间 + `microsecond % 1000`，同秒内只有约 1000 个取值；CR-04 允许同节点多次申请后，`payment_applications.apply_no` 唯一键在并发下被撞 → `sqlite3.IntegrityError` → HTTP 500，本次申请丢失（数据回滚一致）。
- 并发证据：40 轮 × 8 线程并发申请，5 轮各 1 次 500，期望 320 笔仅成功 256 笔。
- 复现：`python <工作区>\_dbg_apply_race.py 40`（临时库 + 随机端口）。
- 待开发修复（建议自增/序列或 UUID/随机后缀），修好后本用例转 PASS 并摘掉 `xfail`。

最后一项 P2-08（图片 OCR）已随 `290273b` 修复：OCR 前先把图片转存系统临时目录，避开 WinRT 访问工作区被拒（0x80070005）；用例改为**默认启用**（测试图片改用系统中文字体 48px 渲染，识别率稳定），无 OCR 环境的机器可显式设 `QA_ENABLE_OCR=0` 跳过。

> 口径统一（284a755 + 尾差归集）：所有路径（新建/科目添加/合同确认/回改/变更）首付都按「原金额+增补金额」，4 节点合计恒等于合同总额（尾差按 质保金→验收→进度→首付 归集），相关断言已全部转 PASS。
> 批次 8 合同变更已通过（11e 共 11 项全 PASS）。

## 八、维护规则

1. 开发每交一批修复：先跑 `python tests/run_qa.py`，禁止修改业务代码来「迁就」用例；
2. 修复生效的用例：摘掉 `xfail='Px-xx'`，确认为 PASS 后更新本文件与 `docs/roadmap.md` 的数字；
3. 出现 XPASS：说明缺陷已变化，按新行为核对用例与基线，更新后重新跑；
4. 新增用例：写清分组、断言正确行为，未实现部分统一 `xfail` 到基线报告编号。
